# Database schema — account foundation

The project uses versioned SQL migrations and `pg` directly; there is no ORM. `database/migrate.ts` applies ordered migrations under a PostgreSQL advisory lock and records the file names in `schema_migration`. `database/seed.ts` inserts the current validated level/recipe content; campaign IDs remain stable.

## Tables

- `player_profile`: stable UUID, display name, unique player code, Guest token digest or normalized email/password hash, merge alias, creation and last-played timestamps, and baseline chef appearance JSON.
- `account_email_action`: short-lived single-use email-verification/password-reset token digests; raw tokens are only sent to the mailbox.
- `player_session`: session token digest, owning profile, create/expiry/last-seen timestamps. The raw browser session token is never stored.
- `content`: authoritative recipe/level catalog. Player progress references stable level IDs here.
- `match_result`: one authoritative simulation result per match ID.
- `match_participant`: unique participant link for each match; supports idempotent result retry and account progress confirmation.
- `player_level_progress`: per-player restaurant and level, completed/win aggregates, best score/stars and service metrics, with an update timestamp.
- `legacy_progress_import`: an opt-in, unverified archive of old browser progress. It does not grant unlocks or rewards.

The database still contains a legacy `currency_ledger` table from earlier groundwork. This Phase 1 adds no currency writer, wallet, shop, purchase or reward flow.

## Migration sequence

1. `001_foundation.sql`: content, match results and original profile foundation.
2. `002_accounts_progress.sql`: Guest/account fields, sessions, campaign aggregates and legacy archive.
3. `003_identity_merge.sql`: non-authenticating Guest aliases that preserve live match references during account merge.
4. `004_email_auth.sql`: nullable email for legacy usernames, normalized unique email index and updated identity constraints.
5. `005_profile_progress_scope.sql`: last played/default chef profile fields and restaurant-scoped progress.
6. `006_email_verification.sql`: verified-email timestamp and expiring, single-use email action tokens; pre-existing email accounts are grandfathered as verified.

Migrations are additive to preserve existing profiles. The email migration intentionally does not invent email addresses for legacy username accounts; those accounts can continue to log in by username until a future verified email change flow is implemented.

## Transaction and trust boundaries

Account registration/login/merge and match finalization use transactions. Identity merge and match finalization share a lock order to avoid lost/doubled progress during a live match. Match writes happen only from Colyseus room state generated by the server simulation. No browser endpoint accepts a result payload. Progress remains scoped by stable player UUID; display names are never identity keys.

For local migration testing, point `DATABASE_URL` only at an isolated disposable database, then run:

```powershell
npm.cmd run db:migrate
npm.cmd run db:seed
npm.cmd run test:db
```

The integration tests require a database whose name contains `_test` and delete only their own fixture rows/schemas. Do not use a player or production database.
