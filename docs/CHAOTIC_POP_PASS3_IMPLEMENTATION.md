## Targeted improvements

- `world-art.ts` centralizes material archetypes and five restrained light profiles. Builders select finishes at construction time using semantic asset names and an explicit food-root flag. Color/quantized finish still determines the shared material cache; no per-frame material/texture generation. Food is dielectric, fabrics matte, wood distinct from ceramic/metal. Unknown names retain their authored finish; this is not a complete replacement material atlas.
- Rebalance the existing hemispheric and directional lights per venue: warm diner, fresh coastal, Mediterranean warmth, lantern warmth/cool fill, cool orbital fill/warm edible highlights. Shorten the directional shadow and soften opacity, especially on dark floors. Keep common tone mapping, two lights, existing profile map/cadence and no SSAO/bloom/new postprocessing.
- The five authored floor layouts are preserved. Visual floors now meet the nominal ground plane, matching table feet and input/navigation height. Cabinet/booth/pedestal/bin bases are extended to meet it; shoe placement also meets the plane. A small floor-mesh Y correction does not move stations or simulation coordinates. Touch/floor controls require regression verification.
- Cabinet/seat and wall-floor contacts join the existing worktable contact batch. One transparent vertex-color mesh/material, no texture or extra render pass. Contacts remain in Low and cannot intercept touches. Existing small baseboards/skirting and theme architecture remain; no arbitrary prop clutter or gameplay occlusion.
- Chef/customer hat, hair and apron get identity attachment roots beneath existing head/torso pivots, separately batched. Root metadata supplies a visual rig version/slot names and the unchanged held anchor. Current animation hierarchy and four coat colors remain. This prepares asset replacement; it is not a creator/equip/ownership/network API.
- Maki rolls have larger nori/rice geometry and filling above the rice cap; previously the solid rice cylinder hid it. Regional plates reuse their actual third prepared recipe component to distinguish protein/crisp/premium/late branches. Orbit uses the actual protein/greens/bread or mushroom/comet components rather than identical colored pellets for all recipes. No cooking graph/timing changes.
- Extend the offline runtime inspection page with the actual Little Sun level-10 equipment kit. No server room or invented gameplay snapshot. Gameplay/asset-study evidence stays labeled separately.

## Performance and bundle

Final Pass 3 initial JS/preload graph: **44 files, 1,819,088 bytes / 497,537 independent gzip bytes**, measured from the built game HTML. That is +4,529 raw bytes / +1,795 gzip bytes against Pass 2; no bundle reduction is claimed. The existing large shared Babylon warning remains.

Retina resolution is unchanged. Touch Balanced/Low/High keep 30/24/60 targets, hidden-tab suspension and 512px/10 Hz Balanced shadows. Matched 1920×1080 captures show draw calls falling from 308→296 (Little Sun), 274→267 (Tide), 283→272 (Olive), 275→265 (Lantern) and 284→280 (Orbit). Triangle estimates change by about −0.3% in each scene; estimated geometry bytes by roughly −0.2%, with texture bytes unchanged. Shadow casters fall by 4–5%. These are scene counters, not measured GPU time or battery improvement. The screenshots and JSON counters are under `screenshots/chaotic-pop-pass3-before/` and `screenshots/chaotic-pop-pass3-after/`.

The Pass 2 initial game/preload JS graph was 1,814,559 bytes / 495,742 independent gzip bytes. Vite's largest shared `preferences`-named chunk is about 796 kB and contains shared Babylon dependencies, not just preferences code. Other large emitted chunks include lazy glTF (~455 kB), scene (~122 kB), PBR shaders (~120 kB each), texture tools and image processing (~117 kB each). Emitted size is not equivalent to initial download. The game currently imports KitchenScene in `main.ts`; the GLB loader is already dynamic. A later loading change should dynamically import scene construction at game entry, audit builder/engine dependencies and loading cancellation, and measure the actual preload graph. No chunk-threshold suppression or behavior-changing split is applied for a cosmetic size claim.

Counters are Chromium SwiftShader workload/estimated buffers, not actual VRAM, native FPS, phone temperature or power. Startup samples are included until the 240-frame window rolls out. New local diagnostics record synchronous kitchen build time and time from build start until scene readiness, once per rebuild; these are client construction/shader readiness, not end-to-end network loading time. The baseline lacked these fields, so no before/after load-speed claim is possible. Real iPhone 13/14 Pro Max verification remains required: Balanced + Retina balanced, same brightness/busy four-player shift, 10–15 minutes, orientation/background/reconnect, telemetry and heat/touch/clarity comparison. High remains more expensive.
